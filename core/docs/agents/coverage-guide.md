# Code coverage

How this project reads and maintains its coverage page, and the optional browser and combined figures. Moved from AGENTS.md in 3.3.0, unchanged in substance; AGENTS keeps the trigger. The policy on what coverage proves and on optional enforcement is in [maintenance guidance](maintenance.md), "Incremental quality policy".

`docs/agents/coverage.md` shows, per folder, how much of the code the unit tests run (lines, statements, branches, functions) and the files no test runs; `npm run coverage` (or the stack's coverage run, then `node tools/coverage-table.mjs --write`) refreshes it and its baseline. CI prints the current table and warns when a folder drops more than `coverage.drop` points; projects opting into `coverage.enforce` fail the check against the main-branch baseline instead. Coverage says what ran, not that the behaviour is checked: a table to find untested parts, never a number to hit. The committed page and baseline change only in a PR that changes coverage on purpose (code removed, tests added for it) and in audits, never as a side effect of other work: CI prints the live table on every PR anyway, and parallel PRs that each rewrite the page conflict.

## Browser and combined coverage (optional)

Unit coverage says what the unit tests ran. A project with browser tests (Playwright) can also measure what they ran and what either ran, each as its own table: `tools/browser-coverage.mjs`.

1. Run the browser tests in Chromium, the only browser with a coverage API (the collector says so in any other), with the collector in a Playwright fixture: `startBrowserCoverage(page)` before the test and `stopBrowserCoverage(page, 'coverage/browser', testInfo.testId)` after it. It saves the V8 coverage of each script with its source map (without the sources themselves), one file per call, so retries and several pages per test never overwrite a run; serve source maps in that build.
2. `npm run coverage:browser` (`node tools/browser-coverage.mjs`) maps the runs back to the files under `coverage.folders` (required here) and writes `coverage.browser.summary`; with `coverage.combined` it adds the unit run's LCOV (`coverage.lcov`, with line records) and writes `coverage.combined.summary`, where a line counts as covered when either ran it, and once; for a file the unit run measured, its executable lines are the lines (a source map also marks imports, decorators and type-only lines), so the combined figure stays comparable with the unit one. The same script seen in several tests counts as one file. Sources it cannot match to a file here and scripts without a source map are listed and left out, never guessed; a bare file name never matches by suffix; vendor code (`node_modules`), bundler runtime (`webpack/…`) and virtual modules (`angular:…`, `<…>`) are left out quietly.
3. `coverage-table.mjs` then prints and writes a "Browser tests" and a "Combined" table next to the unit one, with their own baseline keys (`browser:<folder>`, `combined:<folder>`) and the same drop rule; a configured summary that is missing is reported, and fails under `coverage.enforce`. Under enforce, the PR that adopts a run starts its baseline (nothing to compare yet), and a PR that removes a setting while the main baseline still has its rows is reported, so a regressed run cannot be hidden.

These figures are lines (and statements, equal to lines): branches and functions are not measured from the browser, so those columns show "–". Unconfigured projects see no change. Browser coverage says what code ran during browser tests, not that the screens are right: visual and accessibility checks stay separate.
