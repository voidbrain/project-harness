# Prerequisites and the work queue

Read before you add a prerequisite or reorder the queue. Part of the [backlog rules](../BACKLOG-RULES.md).


## Linked prerequisites (optional)

Adopt `tools/backlog-dependencies.mjs` when explicit sequencing is useful. In a record's details metadata table, maintain one optional `Depends on` row. Each entry is `[F-019](#f-019) — required outcome`, separated by `<br />`; omit the row or use `—` when no prerequisite is declared. Link local records in the active backlog or `archive/backlog-<year>.md`; after archiving a prerequisite, update its active dependents' links. Keep original archive lines unchanged. An active reopened record takes precedence over its archived history. Archived dependency links resolve by stable ID to the current record location; their historical URLs remain unchanged.

Prefer step-level prerequisites (8.8.0): when one step needs one step of another record, put that step's ID in the waiting step's `dependsOn`. The generated Depends on and Unlocks cells then name the step, the waiting step's status says `waits on <step>`, and the rest of both records stays free. Keep a `Depends on` row only when no single step can be named yet, with the reason; `check:work` lists such rows so they get narrowed. Record hard prerequisites and the particular contract, release or acceptance outcome needed. A prerequisite may constrain only part of an item; record that scope and continue independent work. Related improvements belong in ordinary related links. A dependency does not automatically change Status, Human action required or verification, and a closed prerequisite does not prove its required outcome was delivered: inspect its resolution and evidence.

`node tools/backlog-dependencies.mjs --check` validates local references, duplicate dependencies, self-links and local cycles; run it in CI when adopted. Maintain only Depends on. With source-owned records (`workItems`), `work-items build` shows each active record's prerequisites and its direct dependents in a generated `**Depends on:** … · **Unlocks:** …` line under its summary table, and fails on an invalid graph or a record with links but no summary table; a hand-edited ledger shows only the authored Depends on rows, without Unlocks; Unlocks lists direct dependents and is not a readiness claim. An absent field means no declared prerequisite, not proven independence. Existing records require no migration. (Until 5.4.0 the tool wrote `docs/agents/backlog-dependencies.md`; a leftover page now fails the check until it is deleted.)

Use `[owner/repo:F-019](https://github.com/owner/repo/blob/<ref>/docs/BACKLOG.md#f-019) — required release or outcome` for an external prerequisite, with its actual owner/repository and ref. External links are explicitly not checked live: existence, status, outcome and cross-repository cycles need review. The [ownership and dependency-direction rules](ownership.md) still apply: a project can depend on an upstream release; a reusable master stays independent of downstream adoption. A solution coordinator may depend on its component releases and owns its integration acceptance. Generated backlinks cover this repository's declared edges only.

## Optional work queue

Priority is an authored impact judgment and can be reassessed; it is not a completion score. To deliberately prioritize a record or sequence, optionally add `| Queue order | 1 — Owner-selected next |` to details. Use unique positive integers and a reason among active records. An order does not clear a human action, a named blocker or a required prerequisite outcome.

`node tools/backlog-queue.mjs --check` validates the queue: priorities, effort, human cues, unique Queue order values and prerequisites. With `workItems.order: "queue"` the generated ledger lists each group's records in queue order (a `{"records": "all"}` layout segment makes bugs and features one group, so the whole ledger reads in priority order): impact priority first, then within a priority agent candidates, records waiting on a prerequisite review, a human action, or a named blocker; each record's own cue, status and Depends on line show which. Within a lane the order is Queue order, configured roadmap placement, direct active dependents, remaining-effort category and ID. A blocker is listed above what it blocks: an open prerequisite in the same group, with its own prerequisites first, moves up to just above the first record that waits on it, whatever its priority or lane; every other record keeps the priority order. It never changes source records, calculates a weighted score or infers permission or verification. Open or external prerequisites require review; scoped dependencies can allow independent slices, and a closed prerequisite still needs its required outcome checked. (Until 5.4.0 the tool wrote `docs/agents/backlog-queue.md`; a leftover page now fails the check until it is deleted.)

Optional `.harness.json` setting: `"workQueue": {"roadmap": "docs/ROADMAP.md"}`. The roadmap placement table has a Records column and Scope or Acceptance column. The queue displays that context without changing milestone status. Without that setting no roadmap order is inferred. An optional Impact metadata row may explain the authored priority; it is not a numerical score. Reassess ordering from actual risks, user goals, evidence and uncertainty, not from record age or a percentage.
