# Backlog maintenance rules

This is the authoritative update and review procedure for the [Project harness backlog](BACKLOG.md). AGENTS and README link here; keep procedural changes here rather than adding competing instructions elsewhere. The backlog's lifecycle table is the status quick reference. Archives and audits preserve dated evidence, not current state.

## One repository, one backlog

Each backlog owns the work of its own repository and nothing else (single responsibility). Dependencies point one way: a repository may wait on what it uses, never on what uses it. For this repository, the projects that apply the harness are downstream.

- **Here.** A record tracks a change made in this repository: template text, tools, procedure. Its next action is a step taken here, and it closes on what this repository shows: the PR merged on a green CI and, for a release, its tag on GitHub.
- **Downstream: never wait for a project.** A release record closes on its tag. Reconciling a project with it is that project's work: its `check:freshness` reports the release at its next session start, and its own backlog records the reconcile. "Closes when both projects report it" is the wrong condition.
- **Evidence from projects** may supplement owned fixtures: cite an already completed consumer trial in Verification. It is optional evidence, never a required pre-tag trial or a pending consumer gate.
- Link a project's record when it matters (the request that started a change, a failure it found); never track its status here.

Test: if a record's next action or closure condition can only happen in another repository, it is in the wrong backlog. Move that part to the backlog it belongs to and link it.


### Ownership rejection and dependency direction

Reject an active record during review if its Issue, next action or closure criteria assign work to a different repository. Split that work into the owning repository's backlog and retain only an upstream dependency link or dated evidence here. A downstream adoption reminder is still foreign work when hidden in details, labelled a follow-up or placed after the release step. Check all three places, not only the title. This is a semantic review requirement; the layout validator does not establish ownership.

Apply single responsibility and dependency inversion to architecture and delivery: a reusable master/template/library owns generic contracts and behaviour; derived projects depend on those contracts through their own adapters or configuration. A master must not import derived-project implementation, require its private state or deployment, or make its release, acceptance or closure wait for downstream adoption. Required regression tests use repository-owned fixtures and contract tests. An already completed consumer trial may be cited as evidence; it never becomes a pending downstream release gate. Product-specific requirements stay in the product repository.


### Solution coordinators

An optional solution repository owns architecture/contracts, compatibility, coordination and end-to-end integration acceptance. It may legitimately depend on its component releases; this is composition, not a reusable master depending on derived consumers. Components retain their own implementation records and close them on their own acceptance. The coordinator's next action can be defining a contract or running integration checks, never doing a foreign repository's implementation under its own ID. Use the [solution profile](agents/solution-profile.md) and qualified `Components` links. Generated dashboards are read-only snapshots, preserve source ownership/revisions and report missing sources as unknown; never edit copied statuses or average completion percentages. A generic harness release uses its own fixtures and never waits for a real coordinator to adopt it.

## When to update and review

- A plan or promise given to the user (steps, a table to build, a later fix) is recorded at once: a new record or the next action of an existing one, in the same change as the reply that makes it. A plan that lives only in the conversation is forgotten.
- Every code, documentation or asset change and every PR updates the affected bug/feature records. Add a stable ID if needed; maintenance-only changes belong in Other changes. Do not create a new ID for each follow-up PR.
- At PR creation, add its actual link and distinguish implementation, investigation, partial fix and verification. Replace temporary PR placeholders once the PR exists.
- After a PR merges, when CI/verification finishes, when the user supplies acceptance or a new failure, and at the start of work on a related item, reconcile the affected records using the procedure below. Reconciling a merged PR is part of the next working PR, not a PR of its own: a verification-only or reconciliation-only PR is opened when `check:freshness` marks the backlog due (10 merged PRs or one day behind by default) or when no working PR follows. The evidence required for each status is unchanged; only where it is recorded changes.
- When asked for backlog status or an audit, review every active record. During ordinary work, review related items and any contradictions encountered; a row's age alone is never evidence that it is fixed, abandoned or invalid.
- Review and repairs require an active agent execution host. Session-start freshness checks report merged changes, branches, newer harness releases and missing/stale/blocked audit areas; remote fetch failures remain explicit. The daily read-only maintenance workflow also checks review evidence. Follow the [audit procedure](agents/audit.md) for scope-aware dated reports. Audit age warns by default and fails when `audit.enforce` is enabled; malformed audit metadata and enabled maintenance receipt gates fail independently. Never claim automatic repairs or continuous agent review from scheduled checks alone.
- Parallel PRs all edit the backlog, so when one merges the others often conflict there. Resolve in the conflicting PR (AGENTS allows a conflict-only push to a green PR): keep every record from both sides, keep the newer header and move it to the current `main` with the CI of the PRs merged since. Never resolve by taking one side whole.

## Review procedure

1. Read current main and preserve the user's edits. Identify every item affected by the PR/change, including shared dependencies and maintenance records. Reject foreign-repository actions and downstream completion gates under Ownership rejection and dependency direction before publishing.
2. Check the actual PR target, merged state, commit and CI jobs (`npm run ci:status -- <PR numbers>` lists each job, failed and retried tests, and PRs not based on main). Read failures or selected test results when needed. A merge is not verification; a green workflow only establishes the checks it actually ran. Skipped jobs, mocked devices and captured screenshots do not establish the behaviour they did not test.
3. Compare acceptance requirements, status, next action and verification evidence. Remove obsolete present-tense pending claims after their checks pass; move relevant earlier failures to PR / evidence as labelled history. Record unresolved checks explicitly. If a requirement is ambiguous, investigate rather than invent acceptance or claim closure.
4. Choose the supported state using the lifecycle legend. Implemented means required checks remain. Verified requires all recorded acceptance checks to pass with dated evidence; when every one of them is automated (the PR's own tests and CI, as for tooling and record changes), the merged PR's green CI run is that evidence: cite it. Close only a Verified record, or a cancelled or superseded one with its reason; a reconcile may verify and close in one edit, naming the run. When no action remains, record the resolution and close/archive; agents need no extra permission unless the item explicitly requires human acceptance. Failed checks return the item to Open/Investigate as appropriate; record a named blocker only when it actually prevents the next action.
5. Reassess Human action required and blockers. Yes means the next action depends on explicit human acceptance, a human decision (choosing an option or a scope), private evidence or real devices. When an agent asks the user to decide before continuing an item, set that item's cue to Yes in the same change, naming the decision; set it back once answered. No means an agent can advance the next step, not that the item is done. Do not require a human for ordinary coding or automated/browser checks. A blocked record states the missing input/dependency and the condition for resuming.
6. Update PR/evidence, verification, next action and Reviewed together. Check related records for contradictions, such as a passed check still described as pending, a Verified item awaiting a required human check, or a completed maintenance change left yellow indefinitely.
7. Validate table structure, markers, links and dates before publishing. Add the actual follow-up PR link, and reconcile again when its checks finish or it merges: a PR's records name it by number: write "this PR" only until the PR exists, then replace it with `#N` and push at once (on the PR's CI run `check-backlog` fails on a placeholder the branch adds, and on any already on the default branch, where it would fail every other PR), and a record that said "close when this PR merges" is verified and closed in that reconcile. A conflict in the backlog is merged record by record (`node tools/merge-backlog.mjs`).

Staleness prompts review, not a status change by itself. During a full review, flag unresolved dependencies, outdated PR placeholders, missing next actions, old pending claims and long-held Verified records. Keep the last honest evidence date if no new check ran; Reviewed may advance only after actually reviewing the record. Do not reset Opened or fabricate implementation/verification dates to make a record look current.

## Procedures and tracked outcomes

Record agreed outcomes and unresolved work when accepted, before implementation. Routine required steps (reading relevant code/rules, running applicable checks and reviewing ownership) belong to the procedure, not a separate bug/feature each time. Put an item's required acceptance checks in its Check recap/details; a failed check or deferred required action updates that item with the blocker, evidence and next action. A separately owned outcome gets its own record; never duplicate the same work as checklist IDs.

Mandatory means applicable steps must be completed or an actual blocker recorded; it does not turn optional integrations into prerequisites. Capability assessment at setup or relevant workflow changes can conclude that existing tools suffice. MCP/skill recommendation and installation remain conditional on useful missing capability and authorization. An impact map covers actual derived outputs; a separate conflict map is warranted by meaningful unresolved rule/interface conflicts, not required as an empty artifact for every project. See APPLY.md in the template repository for the application trigger matrix.

## Record and evidence requirements

- Keep IDs stable and in ID order within each section; never reuse an ID for a different item. A new finding about the same behaviour as an existing record (a failed check, a follow-up, a regression) goes into that record, reopened if it was closed, not under a new ID. `B-nnn` is a bug or reliability problem, `F-nnn` a feature or improvement. Opened is the first known date that ID entered the ledger, not a guessed original-report date; preserve it through reopening.
- Each item records a reproducible trigger/request, scope, next action and closure requirements. Active records show the stable ID heading and a bold title, then a four-column signal table (Signal, Priority, Status, Effort). Keep the human-action line and the Issue / Reproduce / Check table visible for every bug and feature, regardless of actor or whether the record changed. Put the full Next action / closure evidence and the PR history, Opened, Verification and Reviewed metadata in one closed-by-default details block. Priority measures impact: P1 a release that breaks projects or a check that lies; P2 procedure gaps and rules projects need; P3 enhancements and wording.
- PR / evidence identifies actual changes or checks with links and labels. Use `—` if no PR is known. Link the latest relevant evidence without discarding important historical context.
- Verification records date, method, result and evidence separately from Reviewed. Methods: Human, Project trial (a real project's checks before and after), Script (`check:template`, CI) and Documentation. Use Pending where applicable; different checks may have different dates. Verification states the current result: one entry per method, the latest check of it. Earlier results (a failure since fixed, a superseded pass) belong in PR / evidence, labelled with their PR or run, so the cell never reads “Pending; … passed” for the same check. A unit test does not prove visual or field behaviour, and an overall CI result does not replace checking which jobs ran.
- **A bug fix starts with a failing test.** The fix for a B- record commits a test that reproduces the defect and fails without the fix: commit it before the fix, and do not edit that test while making it pass (a changed expectation is a changed requirement: say which). When no test can show the defect (visual, device-only or external-service behaviour), record why and the manual check that replaces it. The record names it in PR / evidence or Verification: `Test: <file or test name>`, or `No test: <reason and manual check>`. `check:backlog` warns when a branch makes a B- record Verified or Closed with neither in those cells.
- **Independent review.** A PR that closes a P1 record or changes a harness file (a file listed in `.harness.json`, or the template itself) gets a review in a fresh context before it merges: a review skill or a separate session that did not write the change reads the diff and the record's Check for bugs, security and compliance. Its findings are fixed in the PR or answered there. The record cites it: `Review: <how, outcome>`. Documentation-only and small (a few lines, no behaviour) changes are exempt; a P1 record says why: `No review: <reason>`. So is a reconcile whose only harness-file changes are byte-identical copies of `copied` files from a published template tag, their `copied` entries and the `version` stamp, when `node tools/check-harness.mjs --strict` passes on the PR head (it exits 1 if any copied file differs or the template is missing); the record cites it as `No review: check-harness --strict matched vX.Y.Z`. Any adapted file (AGENTS.md and BACKLOG-RULES included), forked or project-written change, or a P1 closure in the same PR still needs a reviewer. Match the reviewer to the change: mechanical checks (byte copies, version bumps, a reformat whose syntax tree is unchanged, regenerated views) can run on a smaller, cheaper model with an explicit list of what to verify; design, safety rules, security, data migration and lifecycle code get the strongest available model. The checks required do not change with the model. In Claude Code the copied agent definitions pin the model: `mechanical-reviewer` (Haiku) and `design-reviewer` (Opus), both instructed to report and never edit or merge; other clients follow the rule through their own settings, and the work-usage ledger records which model actually ran. The reviewer reports; it never approves or merges. `check:backlog` warns when a branch makes a P1 record Verified or Closed with neither; `check:freshness` reminds a branch that changes harness files.
- Reviewed is when status/evidence were actually reconciled, not an inferred merge date. Preserve existing dated history; do not invent dates.
- The human-action line is visible in every active record, icon first: `🧑 **→ Human action required: Yes**<br />One short sentence naming the human action or decision.` or `💻 **→ Human action required: No**<br />One short sentence naming the next action.` Keep that sentence short; long plans belong in details. Immediately below it, every record has a two-column table under `| | |` / `|---|---|`, with exactly three rows: `| **Issue** | … |` (the problem or request), `| **Reproduce** | … |` (where and how to trigger it, or the workflow to exercise for a feature), `| **Check** | … |` (observable acceptance criteria or the decision options). No actor or untouched-record exemption. One manual review can cover related IDs; reference the shared item. A `---` line follows every record’s details.
- Effort estimates remaining work, including investigation, implementation and verification: `🟢 Small` (up to one focused day), `🟡 Medium` (two to three days), `🔴 Large` (four or more days). Colour always accompanies the word. Record a dated rationale, assumptions and uncertainty in details; an optional range such as 2–4 hours or 1–2 days can make that estimate more useful. Reassess effort when scope, dependencies, implementation or verification changes, and review related records. Keep pending acceptance in remaining effort. Status and verification evidence describe progress; completion percentages are removed from active records. Model tokens/cost are separate usage or budget measurements/estimates, not a measure of remaining project work.

## Linked prerequisites (optional)

Adopt `tools/backlog-dependencies.mjs` when explicit sequencing is useful. In a record's details metadata table, maintain one optional `Depends on` row. Each entry is `[F-019](#f-019) — required outcome`, separated by `<br />`; omit the row or use `—` when no prerequisite is declared. Link local records in the active backlog or `archive/backlog-<year>.md`; after archiving a prerequisite, update its active dependents' links. Keep original archive lines unchanged. An active reopened record takes precedence over its archived history. Archived dependency links resolve by stable ID to the current record location; their historical URLs remain unchanged.

Record hard prerequisites and the particular contract, release or acceptance outcome needed. A prerequisite may constrain only part of an item; record that scope and continue independent work. Related improvements belong in ordinary related links. A dependency does not automatically change Status, Human action required or verification, and a closed prerequisite does not prove its required outcome was delivered: inspect its resolution and evidence.

`node tools/backlog-dependencies.mjs` generates `docs/agents/backlog-dependencies.md` with linked **Depends on** and reverse **Unlocks** lists. Maintain only Depends on; the generated Unlocks list shows direct dependents and is not a readiness claim. An absent field means no declared prerequisite, not proven independence. Run it after affected record changes and archiving; run `node tools/backlog-dependencies.mjs --check` in CI when adopted. It validates local references, duplicate dependencies, self-links, local cycles and page freshness. Existing records require no migration.

Use `[owner/repo:F-019](https://github.com/owner/repo/blob/<ref>/docs/BACKLOG.md#f-019) — required release or outcome` for an external prerequisite, with its actual owner/repository and ref. External links are explicitly not checked live: existence, status, outcome and cross-repository cycles need review. The ownership and dependency-direction rules above still apply: a project can depend on an upstream release; a reusable master stays independent of downstream adoption. A solution coordinator may depend on its component releases and owns its integration acceptance. Generated backlinks cover this repository's declared edges only.

## Visual cues and table integrity

| Cue | Rule |
|---|---|
| First-column status | 🔴 Open · 🟠 Investigate · 🟡 Implemented · 🟢 Verified · 🟣 Blocked · 🔵 Closed; match the written Status. |
| Active priority | 🔺 P1 · 🔶 P2 · 🔹 P3; keep its written label and value. |
| Closed or Blocked priority | ◻️ P1 / ◻️ P2 / ◻️ P3; only the marker changes. Verified priorities keep their colour until Closed. |
| Reopened or unblocked | Restore the colour for the retained priority; preserve ID, Opened and previous evidence. |

Colour never replaces status text, priority labels or evidence. Table rows must be contiguous: a blank line ends a Markdown table. Every row needs its header's number of cells: four for active signal rows, two for metadata, and the original width in historical archives. Escape literal pipes inside cells. Use `<br />` for an in-cell line break. Keep a blank line before a table and after its last row. Validate all affected rows, not just the added one, and check local links and status/priority consistency. For documentation-only changes these structural checks and a deliberate review are enough; do not invent application test coverage.

## Closure and archives

Close fixes after their recorded criteria pass and no action remains; Verified is a transition, not a permanent holding pen. Human/device acceptance is required only where specified. Cancelled, duplicate or superseded items can close without a verified implementation when the reason and replacement link, if any, are explicit. Do not close a reported bug because one attempt could not reproduce it without recording the investigation and the remaining uncertainty.

Move closed records, including completed maintenance-only changes, into the year's archive, `docs/archive/backlog-<year>.md` (one file per year, the year the record closed), linked from the active ledger. Inside it records follow their closing date, under a `## Closed <YYYY-MM-DD>` heading per day; records closed before a project adopted this layout keep a heading of their own. Preserve each complete record (visible actions plus metadata), with original ID/priority, PR history, evidence, resolution and closure date (`Closed YYYY-MM-DD` in its evidence). Historical archive content only grows: add records anywhere and corrections as dated notes, but never change or remove a line already on the default branch; a record may move from one archive file to another, never out of the archives. `check:backlog` compares every line with the default branch (a line no longer in its file must be in another archive file) and fails on a record whose closing year is not its file's. Write an archive by reading it fully first, never by truncating it. Historical Closed records keep their closure cues if an item is later reopened; the active record describes the new work and links its prior history.

Closing a documentation audit or recording change does not close a product feature whose checks remain pending. Put that pending work on its own active item rather than keeping the completed maintenance entry yellow indefinitely.

An optional weekly closure index can precede an archive. Adopt `tools/archive-recap.mjs`, list it in the copied stamp, and run it whenever records move into the archive. It groups features/bugs by recorded closing date, Monday–Sunday, with links to the first section of each week. Only its exact generated `archive-recap` block is replaceable: `check:backlog` recomputes it before excluding that block from historical-line protection. Missing tools, stale/forged recaps or hidden record content fail. Every original record line remains immutable; adding or regenerating an index never verifies or closes product work. Archives without an index need no migration.

## Documentation consistency

README summarizes capabilities; AGENTS directs repository work, with per-area rules in [docs/agents/areas.md](agents/areas.md); this file owns backlog procedure; BACKLOG holds current records and the quick lifecycle legend; the [style guide](STYLE-GUIDE.md) owns writing conventions; [APPLY](../APPLY.md) owns the apply and reconcile procedure; the [CHANGELOG](../CHANGELOG.md) owns release history; `core/` and `angular/` are template content, not this repository's rules. User instructions take precedence. Dated archives and audits preserve context and do not override current rules.

When changing shared rules, reconcile linked summaries and scoped exceptions in the same PR. Keep historical evidence dated rather than rewriting it as current verification.

Derived things (generated pages, translations, recordings, guides) follow the impact map, `impact` in `.harness.json`, chains included (`after`): `check:freshness` lists the rows a branch sets off in run order, and each is done in the same PR or recorded with its reason; `docs/agents/impact-map.md` shows the whole map. The check below covers what the map does not.

For **every modification**, including a backlog-only edit, check README, APPLY, CHANGELOG, AGENTS and its area notes, BACKLOG, BACKLOG-RULES, the style guide and the template files that state the same rule for affected claims, rules, links and exceptions. Update every affected document in the same PR; do not edit an unaffected file merely to mark it reviewed. Preserve user changes. State the consistency check and any outstanding discrepancy in the PR validation notes. A backlog state change can require README or guide corrections even when code did not change.

On every change or review, actively reassess whether each affected status, next action, human dependency, blocker, verification result/date and PR evidence can advance. When the next action is authorized and feasible, perform it; do not merely rewrite an “Agent can…” reminder or stop at a review. Pause only for an actual dependency or missing required human evidence, record it explicitly, and continue independent authorized work. Never advance a state without the required evidence.

Run `npm run check:backlog` after every ledger edit. CI validates active signal widths, remaining-effort colours, words and rationale, visible titles, human cues and all three recap rows on every record, collapsed next actions and metadata, dates, unique IDs, status/priority cues and balanced details. Historical archives remain outside this active-layout schema.

## Optional work queue

Keep the canonical ledger in ID order. Priority is an authored impact judgment and can be reassessed; it is not a completion score. To deliberately prioritize a record or sequence, optionally add `| Queue order | 1 — Owner-selected next |` to details. Use unique positive integers and a reason among active records. An order does not clear a human action, a named blocker or a required prerequisite outcome.

`node tools/backlog-queue.mjs` derives `docs/agents/backlog-queue.md`; `--check` detects stale output. Adopt it with `backlog-dependencies.mjs`. It groups agent candidates, prerequisite-review work, human actions and explicit blockers. Within each lane it orders by Queue order, impact priority, configured roadmap placement, direct active dependents, remaining-effort category and ID; every reason stays visible. It never changes source records, calculates a weighted score or infers permission/verification. Open or external prerequisites require review; scoped dependencies can allow independent slices, and a closed prerequisite still needs its required outcome checked.

Optional `.harness.json` setting: `"workQueue": {"roadmap": "docs/ROADMAP.md"}`. The roadmap placement table has a Records column and Scope or Acceptance column. The queue displays that context without changing milestone status. Without that setting no roadmap order is inferred. An optional Impact metadata row may explain the authored priority; it is not a numerical score. Reassess ordering from actual risks, user goals, evidence and uncertainty, not from record age or a percentage.

## Optional explicit tasks and source-owned records

Projects that adopt `workItems.enabled` follow [parallel work](agents/parallel-work.md): stable parent B-/F- outcomes, one source file per active record, a generated current-status ledger and independently reviewable child tasks. The parent retains status/acceptance ownership; task completion or a claim never clears a human cue, verifies an outcome or grants permission. Non-adopters retain this document's ordinary ledger/record-aware merge procedure. Adopters resolve conflicting source records/layout without losing either side, regenerate the ledger/recap/dependencies/queue/roadmap, then run their existing checks. Published archives remain unchanged. Model suitability requires capability/evaluation evidence, not model-size rankings.

## Optional upfront feature plans

Adopt with `workItems.featurePlans: true` alongside source-owned work items. At feature registration, record the initial anticipated delivery steps when possible; before implementation, require a first plan covering the agreed outcome and its acceptance. An investigation-first plan may name uncertain later work and discovery conditions. A small feature may have one step. Do not reveal only the next step after finishing the previous one.

Each stable task has scope/acceptance, dependencies, status and dated remaining effort with rationale, assumptions and uncertainty. The generated feature table shows every step, its effort and completion. Planned, ready, implemented and verified remain distinct; closed means the step is completed or resolved with an explicit cancellation/supersession reason in its evidence. Completed steps show zero remaining work; never reconstruct an unmeasured original estimate. Git history retains dated estimates and revisions. Parent acceptance, human cues and closure remain independently authoritative.

Refine routine implementation detail autonomously within the accepted scope. Propose material expansion, a split into distinct delivery outcomes or a material effort increase to the owner before adopting it. Preserve the accepted plan, explain the discovery, proposed difference and revised estimates, and mark the pending decision as human action. Record agreement before changing the baseline; no silent scope growth or deletion of unfinished steps. Splitting for display alone does not authorize extra work.

With development usage enabled, label attributable jobs with the feature and stable step ID. Link verification, review and work evidence to the same step; feature reports roll up distinct step jobs. Shared or unattributable work remains explicitly unassigned/unallocated, never duplicated. Operational logs retain their owning system and privacy rules; link only relevant acceptance evidence. Unknown counters remain unknown. These instructions do not install a telemetry exporter, reveal hidden tokens or prove instruction compliance.
