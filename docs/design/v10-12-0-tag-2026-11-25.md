# The mistaken v10.12.0 tag, 2026-11-25

**Status: decided by the owner on 2026-11-25: option B, release 10.12.1.**

What happened: the agent ran the release commands for 10.12.0 (F-095-T02) in one chain after `merge-when-green.mjs 265`. The merge failed (a missing maintenance receipt), but a pipe hid the failing exit status, so the chain went on: it tagged `v10.12.0` on the old `main` `0125a12` (10.11.3 content), pushed the tag and published its Release. The agent then marked that Release as a prerelease titled "DO NOT USE" with a warning, made 10.11.3 the latest Release again, fixed the PR and merged #265 on green CI as `055bebc`. It did not move or delete the tag: that is asked first.

Effect: a project that reconciles to `v10.12.0` gets 10.11.3 files under a 10.12.0 name; `check-harness` compares copied files with that tag.

## Options

| | Option | What happens | Note |
|---|---|---|---|
| A | **Move `v10.12.0` to `055bebc`** (proposed) | Delete and re-push the tag on the #265 merge, restore the Release notes | Moves a published tag: owner approval, and `HARNESS_GUARD_ALLOW` for the push guard. Any clone that fetched the old tag keeps it until it fetches with `--force`. |
| B | Leave `v10.12.0` as it is, release the change as 10.12.1 | A PR sets 10.12.1 and notes that 10.12.0 is a mistaken tag; tag 10.12.1 on `main` | No published tag moves; the version sequence keeps a broken entry. |

## Decision

2026-11-25, the owner (relayed by the coordinator session): **option B**. `v10.12.0` is not moved: it stays a prerelease marked "DO NOT USE", its notes pointing to `v10.12.1`. The F-095-T02 content ships as 10.12.1, whose CHANGELOG entry names it and the 10.12.0 mistake, tagged only after its merge is confirmed and `main`'s CI is green on that commit.

## Lesson

Merge and tag are separate, confirmed steps: never chain a tag or a Release onto a merge command, and never read a merge's result through a pipe that hides its exit status. Before tagging, `gh pr view <N> --json state` reads `MERGED` and `main`'s CI is green on the merge commit. Recorded in AGENTS.md ("Releasing" step 4) and the Procedure area notes.
