# Optional built backlog views (10.14.0)

Part of the [harness procedure](../../APPLY.md). Read when a project adopts built backlog views or a coordinator reads them.

A project with source-owned records (`workItems.enabled`) may stop committing its generated `docs/BACKLOG.md` (F-096, owner decision 2026-11-24: a `backlog-views` branch). Committed views stay the default during this transition; a later major release stops committing them, announced in its own entry. To opt in:

1. Copy, at 10.14.0 or later, `tools/work-items.mjs`, `check-backlog.mjs`, `check-freshness.mjs`, `maintenance.mjs`, `reconcile-draft.mjs`, and `backlog-dependencies.mjs` / `backlog-queue.mjs` if adopted, and `docs/agents/pull-requests.md` and `session-start.md`; re-adapt `docs/backlog/review.md` step 1. Keep a `work:build` script in `package.json`: `"work:build": "node tools/work-items.mjs build"`, as `angular/package-scripts.json` lists it.
2. In one PR, so the ledger and its publisher arrive together:
   - set `workItems.views` to `"built"`, add `docs/BACKLOG.md` to `.gitignore` and run `git rm --cached docs/BACKLOG.md`; `npm run work:build` writes it locally. `work-items check` refuses a ledger that git still tracks or does not ignore;
   - CI: run `node tools/work-items.mjs check` before every step that reads the ledger (it writes the fresh build; the maintenance check reads it too), then the "Which backlog views" step (`id: views`) and the `backlog-views` artifact upload it gates, exactly as `angular/.github/workflows/ci.yml` and `solution/.github/workflows/ci.yml` do. Check out with `fetch-depth: 0` so `check-backlog` can compare with `origin/backlog-views`;
   - publishing: copy `core/.github/workflows/backlog-views.yml` unchanged to `.github/workflows/` and list it under `copied`. It is the one shipped workflow with `contents: write`, on push to `main` only and serialised, in two jobs (10.21.3): `build` (`contents: read`, no stored credentials) runs `work-items publish --prepare`, which builds the ledger and runs the project's publish hooks (below), and uploads it as a one-day artifact; `publish`, the only job with `contents: write`, downloads it and runs `work-items publish --ledger=<file>`, which fast-forwards `backlog-views` with `main`'s tree plus that ledger and never runs a hook. It needs no secret. If an organisation policy forbids write tokens in workflows, or a ruleset blocks the branch, publishing fails: changing either is the owner's repository setting, asked first.
   - publish hooks (optional, 10.21.3, F-100): a project whose own tool writes part of the ledger (a recap, totals) names it in `workItems.publishHooks`, e.g. `"publishHooks": ["node tools/backlog-recap.mjs"]`, instead of forking the workflow. The hooks run in order after the ledger is built and before it is published, in the read-only `build` job only, each with the repository root as its working directory and `docs/BACKLOG.md` already written. An entry is `node <repository script> [arguments]`: the script a relative `.mjs`, `.cjs` or `.js` path inside the repository (no `..`, no symlink), arguments of letters, digits and `_@%+=:,./-` only, single spaces; anything else is refused when the settings are read. Each runs as argv (`process.execPath`, no shell), so a configured string can never reach a shell. A hook that fails, or that changes any file but the ignored ledger, stops the publication. While hooks are set, plain `work-items publish` refuses (it would publish without them); locally, `publish --prepare` shows what would be published. A project without the setting publishes the same views as before.
3. The branch appears with the first push to `main` after that PR. Until then `check-backlog` warns that `origin/backlog-views` is missing and the README link below returns 404.
4. Links: the README links the published view, `https://github.com/<owner>/<repo>/blob/backlog-views/docs/BACKLOG.md` (see the note in `core/README.md`). Solution coordinators copy `tools/solution.mjs` and `docs/agents/solution-profile.md` at 10.14.0 or later: they read the publication of the resolved commit, or rebuild it from a local checkout with their own `tools/work-items.mjs` ([solution profile](../../core/docs/agents/solution-profile.md), "Backlogs and links").

To go back, remove `publishHooks`, set `views` to `"committed"`, remove the `.gitignore` line, run `npm run work:build` and commit the ledger, and delete `.github/workflows/backlog-views.yml` with its `copied` entry (`work-items publish` refuses committed views, so the workflow would fail on every push). The artifact steps skip themselves while `views` is not `"built"`. The `backlog-views` branch can stay or be deleted by its owner.
