# Solution dashboard: reading backlogs

Read before you change how the dashboard reads a backlog, or when it reports a source as Unknown. The first paragraph moved here from [solution profile](solution-profile.md), "Backlogs and links", word for word as it stood in 10.14.1; the second, on remaining hours, is new in 10.15.0 (F-095-T04).

Dashboard readers support current four-column summaries, historical five-column signal summaries and the preceding five-column ID/Item summaries. Historical completion percentages are not displayed or used for ordering. Unsupported or malformed sources are reported as unknown, not silently treated as completed/empty: a summary column the reader does not know by name, an unknown status, or a heading that names an ID but is not a record heading makes that source Unknown with the problem named. From generated ledgers the reader also keeps each record's Priority, Remaining, Depends on and Agent cells and its steps table (status, remaining, Who, Depends on with `repo:STEP-ID`); `node tools/solution.mjs check --json` prints what it read. With `--remote`, a backlog over 1 MB is read through the blob API at the same resolved commit. A repository whose `.harness.json` at the resolved commit sets `workItems.views: "built"` commits no ledger (F-096): the reader takes its publication of exactly that commit from the `backlog-views` branch (locally `origin/backlog-views` as last fetched, remotely through GitHub), or, from a local checkout only, rebuilds it in memory from the sources at that commit with the coordinator's own `tools/work-items.mjs`; the Source table names the way ("view published on backlog-views at <commit>" or "view rebuilt from sources at <commit>"). A publication counts only when its tree is the source tree plus the ledger, as `work-items publish` writes it, never on its message alone. Remotely the newest 1,000 publications are searched; a commit with none (an older one, or one whose views did not change) is read from a local checkout, which rebuilds it. A view it can obtain neither way makes the source Unknown, with the reason; so does a `.harness.json` that is not valid JSON.

The dashboard's "Remaining effort" section gives each backlog's remaining agent and owner hours, coordinator included: from its generated totals line (`**Remaining effort:** …`), else the sum of its open records' Remaining cells, labelled as that project's own, uncalibrated estimate, with its open records counted by priority and by size. A backlog it cannot read in hours (estimated only in days, or no totals line and no Remaining cells) shows Unknown, and the solution line then reads "at least N h"; days beside hours in a totals line are left out and make that backlog partial. No percentage appears anywhere, combined or per project. Configure archive files when records close: linked archived records remain readable; active records take precedence when an ID reopens. Unlinked archived records are omitted from component tables. Older archive tables without record headings require explicit migration or a different reader; the tool reports them rather than guessing.

After its source table the dashboard gives the owner view, read only. Each open step (or record without steps) gets a state: Ready (an agent can start it; an implemented step that only awaits its verification is Ready but never the next pick), Owner (it waits on the owner's procedure or decision), Waiting on another item that can still move, Blocked (its prerequisite chain ends at an owner step, an unknown or unavailable prerequisite, a cycle, or a record marked Blocked, which blocks its steps; the root cause is named, in this or another project), or Done. Every prerequisite counts: one that is blocked or waits on the owner blocks the item whatever the order of the list, and a record without steps honours its own Depends on. A step that names both an agent and an owner face (one actor per step is the rule) reads as the owner's. `repo:STEP-ID` prerequisites are resolved in the other repository's backlog at the dashboard's resolved commit; one that is done there but not yet recorded in `externalMet` still waits, and says so. The view has a summary per project (with the manifest's optional `emoji` per repository), the solution order with each item's state and the first Ready one marked "Ready — next", the items waiting for the owner, the blocked items with their root cause, the projects with nothing to do and why, and each project's open steps, collapsed. It never changes a source and never orders work against an owner decision.

The owner view ends with the agent runway (F-097-T01, 10.17.0): per project, the agent hours that can run before work reaches a block, counting open agent work that is Ready or Waiting only on work that can itself run, transitively and across repositories. The blocks that the rest of the work reaches are each named once: an owner step, an unknown or unavailable prerequisite, a cycle (its ring, never looped), a record marked Blocked, or a step whose prerequisites are done but not recorded in `externalMet`. The owner hours that unblock the next layer are those of the owner steps whose prerequisites are done or within the runway. Work behind an owner step is not counted, even when it waits on it through another item. A step whose Remaining cannot be read in hours is listed as not estimated, and the solution line then reads "at least". A prerequisite the reader cannot resolve is a block, never assumed done.

After the runway comes "Audits, reviews and harness" (F-097-T02, 10.18.0): per project, from its own evidence at the resolved commit, its `.harness.json` version against the latest template release (with `--remote` the template's latest published GitHub Release, named by `template.repo`; otherwise the highest `vX.Y.Z` tag of the coordinator's template clone, `HARNESS_HOME` or `template.path`), its newest audit (the newest `docs/audits/*.audit.json` review time, else the newest dated report there) against `audit.days` (7 by default), and each periodic review in `reviews.<name>.days` (`<dir>/<name>/<date>.md` or `<dir>/<date>-<name>.md`, `dir` defaulting to `docs/reviews`). A project behind the template, an audit past its interval and a review missing or past its interval are marked. Missing evidence reads as unknown, never as current; an unreadable manifest is noted.
